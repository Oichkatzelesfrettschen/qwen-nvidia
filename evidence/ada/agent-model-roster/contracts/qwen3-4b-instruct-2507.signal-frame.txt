In the `sendsig` function, the signal frame (`sfp`) is placed **immediately below** the hardware exception frame that the processor writes when it returns from the signal handler. Specifically, the hardware exception return pops an eight-word frame (r0–r3, r12, lr, pc, xPSR) from the stack pointer (PSP), which the kernel sets in `tf_sp`. This hardware frame is stored in `sf_hwframe[8]` of the `sigframe` structure.

The code allocates space for the `sigframe` at an address aligned to 8 bytes (`&~7U`), and then decrements the pointer (`sfp--`) to point to the start of the signal frame. This ensures that the hardware frame lands right after the signal frame — so the hardware frame starts at `sfp + 8` (i.e., `sfp->sf_hwframe[0]`), and the signal context (`sf_sc`) begins right after that. This layout allows the hardware to pop its own frame into the space reserved by `sf_hwframe`, and the signal handler can then access the saved context via `sf_sc`.

The reason `sfp->sf_sc.sc_psr` is set with `regs->tf_psr &= ~XPSR_STKALIGN` before the handler runs is to **prevent a stack alignment fault**. The ARMv6-M architecture specifies that if the `STKALIGN` bit (bit 9) in the xPSR is set, then when the processor returns from an exception, it will adjust the stack pointer by adding 4 bytes (i.e., `sp += 4`). If this happens, the handler would start on a misaligned stack, which is invalid. By clearing the `STKALIGN` bit in the saved xPSR before the handler runs, the processor will not perform this stack adjustment, so the handler starts on the correct, aligned stack. The `sigreturn` routine later restores the original xPSR, ensuring the stack is properly restored when the handler exits.
