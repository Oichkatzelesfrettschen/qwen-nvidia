# What concurrency does to a decode token, preregistered

Every decode number in `evidence/ada/` was taken at one sequence. llama-bench
decodes a single stream, `--parallel 1` sits in every served argv this tree
writes, and the three levers refuted against the 5.1% floor each named a
concurrent served workload as the regime that recomputes its own bound:
`../projection-fan-out/` says its table recomputes where the mat-muls move to
MMQ, `../decode-node-trace/` demoted graph prewarming to a mixed served
workload, and `../graph-loop-bound/` says the same of the 140-microsecond host
round trip. This arm runs that regime.

## The mechanism the arm rests on

`update_slots` builds one batch across every slot holding a token to decode, so
N decoding slots make one ubatch of N columns. `ggml_cuda_should_use_mmvq` reads
`ne11` and selects the mat-mul family from it, so the slot count is the column
count and the column count picks the kernel.

A pre-check settled this before the sweep was written rather than after it was
interpreted. One `--parallel 4` server answering four concurrent requests
launched `mul_mat_vec_q<(ggml_type)12, (int)4, ...>` 14832 times and
`mul_mat_vec_q<(ggml_type)14, (int)4, ...>` 2576 times, so Q4_K and Q6_K both
ran at four columns and the slots co-batch as claimed. The same run read
`n_ctx = 16384` against `new slot, n_ctx = 4096`, which is the division below.

## The confound the arm removes

`llama_context` sets `cparams.n_ctx_seq = cparams.n_ctx / cparams.n_seq_max`
(`src/llama-context.cpp:293`). A sweep holding `--ctx-size` fixed therefore
shrinks each slot's depth as 1/N, and KV traffic per sequence falls exactly as
concurrency rises, which flatters the scaling curve by the confound. Each arm
asks for `N * slot_depth` and reads the per-slot depth back out of the server's
own load line, so the division is observed rather than assumed.

Depth is an axis rather than a nuisance because the two traffic terms move in
opposite directions: weight traffic is amortized across the ubatch and is
constant in N, KV traffic is per-sequence and linear in it. This campaign fixes
the per-slot depth at 4096 and states that as its scope; a second depth is a
later arm.

## Where this closure's thresholds sit

The promoted closure `88681bf4d161` carries the AD104 crossover patch, whose
cmake entries read `GGML_CUDA_ADA_MMVQ_Q6_K_MAX_BATCH_SIZE=10` and
`GGML_CUDA_ADA_MMVQ_Q8_0_MAX_BATCH_SIZE=16`, while Q4_K keeps the upstream
constant of 7 (`mmvq.cu`, the Ada branch of `ggml_cuda_should_use_mmvq`). The
sweep is `1 2 4 7 8 10 11`, which brackets both flips on the 2B:

| level | Q4_K path | Q6_K path | pass |
| ---: | --- | --- | --- |
| 1 to 7 | MMVQ | MMVQ | uniform |
| 8 to 10 | MMQ | MMVQ | mixed |
| 11 | MMQ | MMQ | uniform |

The 0.8B is Q8_0 throughout at a threshold of 16, so it stays on MMVQ across the
entire sweep. That is the control the dispatch claim needs: a kink the 2B shows
at 8 or 11 and the 0.8B does not show is dispatch; a kink both show at the same
level belongs to the roofline or the host and dispatch is invisible at request
level.

## What is measured

One llama-server per level at `--parallel N`, answering N concurrent requests
that carry one prompt, one `n_predict`, and `ignore_eos`. A request that stopped
early would drop the batch to N-1 and decode its tail at a column count the arm
did not ask for, so `ignore_eos` is what holds the batch composition for the
whole window. The first burst at each level is the uncounted warm-up, since
every column count in the sweep is a distinct kernel instantiation paying its
module load on first use.

Two rates, because they answer two questions. The aggregate divides every token
a burst generated by the wall time the burst occupied, which is what the
appliance delivers. The per-request rate divides one reply by the server's own
`predicted_ms`, which is what one client waits through. Both are medians over
four bursts.

The control is the served N=1 arm of this same harness rather than any retained
llama-bench figure. `../graph-loop-bound/` measured its 139 to 140 microseconds
under llama-bench, which calls `llama_decode` and `llama_synchronize` with no
sampler on the host at all, while a served arm runs the full host chain that
`../backend-sampling/` measured at 0.166 ms per token. Comparing a served N=8
round trip against that 140 microseconds would charge the sampler to
concurrency.

## Falsifiers, stated before the run

1. **Slots do not co-batch.** Every capture reads column count 1 whatever N is,
   `ne11` never rises, and the dispatch half of this arm evaporates. The
   pre-check above already refutes this, and it is retained as the falsifier the
   pre-check was run against rather than removed.
2. **Aggregate throughput does not scale.** Aggregate tok/s at N=4 sits within
   the run-to-run spread of N=1, which would say the device is saturated by one
   sequence and that the weight read is not the term concurrency amortizes. The
   `../ncu-decode-baseline/` reading of 444.7 GB/s against a 442.61 GB/s
   reference argues against it, and a refutation here would contradict that
   measurement rather than this design.
3. **No dispatch effect is visible at request level.** The 2B's aggregate curve
   passes 7 to 8 and 10 to 11 with no kink beyond the run-to-run spread, and the
   0.8B curve has the same shape. Dispatch would then be real in the symbol
   table and absent from the rate, which is a finding rather than a failure.
4. **The round trip per iteration is flat in N.** One iteration yields N tokens,
   so the term `../graph-loop-bound/` bounded is per iteration rather than per
   token. Flat means the graph loop is deader at concurrency than at batch 1,
   because the same round trip is amortized over N tokens; linear in N means
   nothing changed; superlinear reopens the lever. This is a three-way outcome
   and each branch is a result.
5. **Concurrency costs per-request latency more than it buys aggregate.** The
   per-request rate falls faster than the aggregate rises, which would make the
   serving default a latency-versus-throughput choice rather than a free gain
   and belongs in `qwen-capacity-policy.sh` as a policy question.

## Discipline

`run-concurrent-sequence-sweep.sh` is a `measurement-campaign` in
`scripts/gpu-workloads.tsv` and takes the owner lock itself, launching the
server with `9>&-`. Every arm runs on the promoted closure with no candidate
patch, under a pinned SM clock, with the desktop client set recorded as this
host's standing covariate. `device-environment.tsv` records the driver, CUDA
runtime, toolkit, and kernel the numbers are bound to. Doctrine order is the 2B
first, the 0.8B second.

The raw Nsight report and its database are the largest artifacts a run writes.
Neither is checked in; the per-symbol table and the report's SHA-256 are what
the evidence keeps.
